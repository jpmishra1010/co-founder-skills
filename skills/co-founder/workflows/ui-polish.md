# Improve existing product UI with category-aware visual craft

## Project binding and quality
Resolve the project using `references/project-identity.md`; bind this task to
its project ID, environment and, for visuals, the approved surface/brand bundle.
Read `references/principles/ui-polish.md`. Apply its evidence-backed review
before handoff. Wrong-project context or an unapproved consequential action
is a blocker, not a missing detail to guess.

## Use and context
Use for an existing screen/site, responsive fix, reference-based refinement, or
an approved new visual direction. Read the product task, brand kit, accepted and
rejected examples, and existing design tokens. Read `references/design-system.md`,
then only the relevant category from `references/category-playbook.md`. Use
`references/visual-qa.md` and `references/craft-gates.md` for verification. No access to a browser means visual
verification is unavailable; never claim a screenshot review from source alone.

## Procedure
1. Clarify preserve versus change. Identify the actual screen, user task, states,
viewport, functional requirements, and approved reference. Inspect the running
page before editing when possible. Ask for missing source assets rather than
invent a logo, fake dashboard, testimonial, or product photography.
2. Determine category and context: transactional business app, SaaS landing page,
commerce catalog, editorial, luxury/hospitality, healthcare, education, services,
marketplace, nonprofit, industrial/B2B, or native/mobile. "Premium" is coherent
hierarchy, detail, and usability—not one universal dark gradient style.
3. Inspect accessible relevant references and the actual project screenshots;
record transferable observations and preserve the project identity. Do not
claim visual review from a text description. Audit hierarchy, reading order, density, alignment, type scale, line length,
spacing, contrast, components, interaction states, media quality, and mobile
behavior. Identify the few changes with highest functional/visual payoff.
4. For a new direction, propose distinct layout/typography choices with reasons;
obtain direction approval before a broad redesign. For a scoped repair, keep
layout logic, brand colors, real content, and working functionality intact.
5. Implement a small coherent system: reuse tokens/components, semantic controls,
visible focus, reserved media space, meaningful states, and content-led breakpoints.
Use real evidence and exact original brand assets. Do not sprinkle visual effects
or turn every section into the same rounded-card grid. Never force all brands
into black/ivory or prohibit an approved brand color merely by generic preference.
6. Render, inspect, and revise at desktop/mobile and applicable intermediate
widths. Test content stress, dropdowns, dialogs, loading/error/empty states,
keyboard, direct load, navigation, refresh, and shared site chrome. Keep an
actual before/after record. A preview screenshot is not proof of real-device QA.
7. Route functional changes to impact-map/build-fix/verify-release. Preserve
performance, accessibility, localization, and SEO behavior while polishing.

## Deliverable
Implemented changes, design rationale tied to the user task, actual screenshots,
functional and visual check results, gaps, and any changed tokens/components.
Use the design scorecard as a review aid, not an objective premium/AI detector.

## Done
No unapproved branding replacement, clipped text, fake product states, broken
primary actions, or known critical responsive regression. Obtain human acceptance
of taste; do not promise universally "non-AI-looking" or conversion increases.
